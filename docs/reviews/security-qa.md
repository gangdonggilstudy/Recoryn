# D04 보안·개인정보·오픈소스 및 QA·DevOps·릴리스 검토

상태: **설계 검토안 / 통합 채택 전 / 구현·제품 시험 미실시**. 배정 D04의 두 전문가 관점을 한 문서에 기록한다. 전문 자격, 보안 인증, 실하드웨어 검증을 뜻하지 않는다. 작성일: 2026-11-14.

읽은 기준은 [AGENTS.md](../../AGENTS.md), [온보딩](../collaboration/onboarding.md), [설계 입력](../design-input-v1.md), [협업 규칙](../collaboration/workflow.md), [배정표](../collaboration/assignments.md)다. 검토 시작 시 통합 설계와 검증 계획은 미작성 상태였다. 작성 중 생성된 [통합 설계 초안](../architecture-v1.md) 및 다른 리뷰의 관련 계약을 추가 대조했으며 차이는 12절에 남긴다. 저장소의 `LICENSE`는 Apache License 2.0 문구를 포함하지만 VoiceLocal 소스, 의존성 잠금 파일, 모델, 빌드 산출물은 제공되지 않았다. 따라서 원본 분석·마이그레이션·의존성 적합성 검토를 완료했다고 보지 않는다.

## 2. 보안·개인정보 관점: threat model

### 2.1 보호 자산과 신뢰 경계

보호 자산은 원본 트랙·확정 청크, 전사 초안·정정·편집 이력, 요약·검색 인덱스·화자 정보, API 키, 동의 기록, 삭제 의도 기록, 청크 manifest, 내보내기, 모델·실행 바이너리와 배포 서명 키다. 해시는 무결성 비교 수단이며, 공격자가 manifest와 파일을 함께 바꿀 수 있는 환경의 진위 증명으로 간주하지 않는다.

신뢰 경계는 (a) 캡처와 AI 작업, (b) 사용자 저장소와 작업 임시 파일, (c) UI와 정책·비밀 저장소, (d) 앱과 로컬 추론 데몬, (e) 앱과 외부 API·프록시·다운로드 CDN, (f) 개발·CI와 배포 산출물이다. 외부 음성·전사·LLM 출력·모델 파일·가져온 manifest는 비신뢰 입력이다. 일반 사용자 권한 실행과 사용자별 앱 데이터 디렉터리를 기본안으로 하며 설치 권한을 런타임 권한으로 이어받지 않는다.

동일 사용자 권한의 악성 프로세스, 관리자·커널·드라이버 장악, 물리적 저장장치 분석은 앱만으로 완전 방어할 수 없다는 잔여 위험을 공개한다. Credential Manager를 앱 전용 격리 경계로 주장하지 않는다. 사용자 폴더 접근권한은 디스크 암호화나 평문 미디어의 암호화를 대체하지 않는다. 앱이 OS 백업·클라우드 동기화·외부 제공업체 보관 정책을 통제한다고 주장하지 않는다.

## 3. SEC-01: 제공업체·endpoint·데이터별 동의와 철회 계약

### 3.1 동의 레코드와 작업 바인딩

`ConsentGrant` 제안 필드는 `grant_id`, `provider_id`, `adapter_id/version`, `endpoint_fingerprint`, `purpose`, `data_kinds`, `session_id`, `artifact_versions/range`, `scope`, `issued_at`, `expires_at`, `policy_notice_version`, `grant_epoch`, `status`다. `endpoint_fingerprint`는 비밀 없는 canonical endpoint, API 경로 계열·버전, 고지된 지역/배포 식별자를 묶는다. 비밀 자체, 원문·참석자·절대경로는 grant 감사 기록에 넣지 않는다. 시간 만료는 시계 역행에도 승인 범위를 늘리지 않도록 보수적으로 처리한다.

scope 기본안은 **한 번의 논리 작업**이다. 세션 범위 반복 승인은 별도 선택이며 만료·철회가 가능해야 한다. 앱 전체·모든 제공업체·미래 세션에 대한 영구 승인은 기본 제공하지 않는 안을 권고한다. 분할·재시도는 승인된 작업·데이터 범위와 예산 안에서만 허용한다. 자동 재시도 횟수, 비용 상한, 중복 청구 가능성도 승인 전에 알린다.

고지에는 수신 제공업체, 실제 endpoint의 scheme/host/port/base path, 목적(STT/요약 등), 데이터 종류·버전·범위, 대략적 크기·비용, 확인된 보관/학습/지역 정책의 출처·확인일, 철회 한계를 표시한다. 확인되지 않은 정책은 `확인되지 않음`으로 남기고 무보관·학습 제외를 보장하지 않는다. 해당 어댑터의 데이터 흐름 자체를 검토하지 못했다면 사용을 막는다. 녹음 대상자에게 필요한 안내·동의는 외부 API 전송 동의와 별개이며 적용 지역·이용 맥락의 검토를 대체하지 않는다.

| 변경·행동 | 허용/재동의 규칙 |
| --- | --- |
| STT A와 요약 B 선택 | 각각 독립 grant. A에 준 오디오 동의를 B의 텍스트 권한으로 전용 금지 |
| host·port·scheme·base path·고지 지역·제공업체 변경 | 기존 grant 사용 불가; endpoint를 다시 고지하고 재동의 |
| 모델 변경·데이터 종류 추가·다른 전사 버전 선택 | 데이터 이용·목적·요금·고지가 달라지면 grant 재발급; 단순 표시명 변경과 구별 |
| 프로젝트 가져오기/백업 복원/다른 PC 이동 | grant와 키를 권한으로 복원하지 않음. 이력만 비활성 참고 자료로 취급하고 재동의 |
| 키 교체 | 기존 실행 permit 무효화 후 재평가. 키 변경만으로 동의 범위를 넓히지 않음 |
| 연결 테스트·모델 목록 조회 | 외부 연결 사실을 별도 고지. 미디어·전사 미사용. 인증 키를 보내기 전 대상 검증 |
| 로컬 모델 실패·timeout·GPU 부족 | 클라우드 자동 전환 금지 제안. 사용자가 대체 작업과 새 grant를 선택해야 함 |

### 3.2 철회와 전송중 취소

1. 작업 생성 시에는 grant ID와 데이터 참조만 저장한다. 실제 송신 직전 브로커가 현재 정책·grant epoch·endpoint·세션 삭제 상태·artifact version·비용 예산을 검사하여 단기 `SendPermit`를 발급한다. 이 검사는 재시작·분할·재시도 때도 반복한다.
2. 철회는 같은 정책 직렬화 경계에서 epoch를 증가시키고 대기 permit을 무효화한다. 새 요청·재접속·재시도·새 application-level 본문 write를 막고 실행 중 연결에는 취소를 요청한다. UI가 철회 성공으로 표시하는 기준은 이 정책 변경이 기록된 시점이다.
3. 철회 전에 OS/TLS/라이브러리 버퍼로 넘긴 바이트는 철회 후에도 상대에게 도달할 수 있다. 전송 계층 취소가 원격 연산·저장·청구 취소를 보장하지 않는다. 한 번에 전체 본문을 넘기는 SDK는 그 호출 이전의 최종 정책 검사와 거친 취소 단위만 보장할 수 있으며 UI에 이 한계를 알린다. 엄밀한 청크별 차단을 지원한다고 검증되지 않은 SDK에 그 기능을 가정하지 않는다.
4. 제안 전송 이력 상태는 `NOT_SENT`, `IN_FLIGHT`, `COMPLETED`, `CANCEL_REQUESTED`, `REMOTE_OUTCOME_UNKNOWN`이다. 이 상태는 작업의 `CANCELLED`와 별개다. 송신 여부가 불명확하면 `REMOTE_OUTCOME_UNKNOWN`을 유지하고 성공·미전송으로 단정하지 않는다. 자동 재전송을 중지하고 중복 처리/비용 위험을 보여준다.
5. 원격 삭제 API가 있더라도 기능·권한·보관 정책을 공식 문서와 시험으로 확인한 어댑터에서만 선택적으로 제공한다. 미지원·실패·응답 불명확은 별도 상태로 남긴다. 로컬 grant 철회, 키의 로컬 삭제, 제공업체 키 폐기, 원격 데이터 삭제는 서로 다른 조치다.
6. 취소 전의 유효한 로컬 부분 결과는 R04에 따라 남긴다. 철회/취소 후 도착한 응답은 새 권한 없이 게시·재전송하지 않는다. 늦게 도착한 데이터는 폐기하고 본문 없는 상태만 기록하는 안을 제안한다. 삭제 요청이 있으면 부분 결과 보존보다 삭제 계약이 우선한다.

필수 오류 코드는 의미 계약으로 `CONSENT_REQUIRED`, `CONSENT_REVOKED`, `ENDPOINT_CHANGED`, `NETWORK_POLICY_DENIED`, `REMOTE_OUTCOME_UNKNOWN`을 제안한다. 오류 상세에 URL query·인증 헤더·본문을 붙이지 않는다. 모두 AI 작업 차원의 오류이며 R01의 캡처를 중단하지 않는다.

## 4. SEC-02: local-only 정책 강제와 endpoint 보안

| 정책 상태 제안 | 허용 | 차단 및 조건 |
| --- | --- | --- |
| `LOCAL_ONLY` 기본 | 로컬 파일·이미 설치된 모델. 명시적으로 등록하고 점검한 loopback 추론 연결 | 외부 DNS·HTTP·모델 메타데이터·업데이트 확인·telemetry·라이선스 확인·fallback 등 앱의 외부 요청 차단 |
| `DOWNLOAD_ONCE` | 사용자에게 고지된 모델/바이너리와 승인된 manifest·CDN에 대한 한 작업 | 미디어·전사·API BYOK 키 전송 금지. 범위 종료 시 `LOCAL_ONLY` 유지; 클라우드 동의가 되지 않음 |
| `CONSENTED_JOB` | SEC-01의 유효한 grant/permit으로 바인딩된 요청 | 다른 데이터·endpoint·작업·프로세스에는 권한 전이 금지. 기본 정책 자체는 바꾸지 않음 |

모든 지원 어댑터와 다운로드는 단일 정책/전송 브로커를 사용한다. UI 버튼 비활성화·환경 변수만으로 강제했다고 판단하지 않는다. 추론 worker는 키와 임의 네트워크 권한을 받지 않으며 필요한 전송은 브로커에 요청한다. 제3자 SDK의 자동 다운로드·원격 코드 로드·통계·업데이트를 버전별로 확인하고 명시적으로 비활성화한다. 검증 못 한 경로는 기능을 활성화하지 않는다.

loopback은 IP literal `127.0.0.1` 또는 `::1`과 등록된 정확한 포트·서비스로 제한하는 안을 제안한다. LAN/사설 IP, 임의 hostname, `0.0.0.0`, redirect는 로컬 전용과 같지 않다. 로컬 HTTP 허용은 이 경계에 한정하고, 외부 API/다운로드는 HTTPS 인증서 검증을 필수로 한다. 사용자 지정 CA·프록시·기업 endpoint는 별도 정책 검토 없이 TLS 검증 비활성화로 해결하지 않는다.

호스트 정규화는 IDN·IPv6·명시 포트·대소문자·기본 포트 등을 일관되게 처리한다. URL userinfo, 임의 query 기반 인증, 비 HTTP(S) scheme, credential 전달이 필요한 임의 redirect는 거절한다. 클라우드 endpoint로 loopback·링크 로컬·메타데이터 서비스·내부 주소에 접근하는 SSRF를 막는다. 기업 사설 endpoint는 로컬로 분류하지 않고 별도 승인된 목적지로 취급한다. DNS가 바뀌면 연결 대상이 승인 정책에 맞는지 재검사하며, SDK에서 연결 대상 확인이 불가능하면 그 어댑터의 보안 적합성을 미확정으로 남긴다.

로컬 Ollama 등 외부 데몬이 대신 외부 전송하거나 모델을 자동 내려받을 수 있는지는 별도 검증 대상이다. loopback 연결 사실만으로 데몬의 local-only를 보증하지 않는다. 검증된 오프라인 설정·모델 사전 설치·프로세스별 송신 제한을 사용하고, 이를 입증할 수 없으면 엄격한 local-only 경로에서 해당 데몬 기능을 비활성화하는 안을 제안한다.

브로커는 협력하는 코드의 강제 경계다. 같은 프로세스의 악성 네이티브 라이브러리·임의 플러그인에 대한 OS 격리로 주장하지 않는다. 임의 코드/플러그인은 별도 프로세스와 검증된 OS 송신 제한이 마련되기 전 local-only에서 차단한다. QA는 앱·자식 프로세스·등록 데몬의 접속 시도와 DNS를 관측하며 OS 자체 배경 트래픽과 구분한다. 패킷 관측에 빈 결과가 나왔다는 사실만으로 모든 미래 경로의 비유출을 증명하지 않는다.

## 5. SEC-03: Windows Credential Manager 및 비밀 계약

Windows 공식 문서에 따르면 `CredWriteW`/`CredReadW`는 현재 토큰의 로그온 세션에 연결된 사용자 credential set을 사용한다. 읽은 버퍼는 `CredFree`로 해제해야 한다. 이 API 동작은 근거이며 Python wrapper 선택·실제 호출 성공은 아직 검증하지 않았다. 근거: [CredWriteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew), [CredReadW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw).

| 계약 제안 | 처리 및 수락 조건 |
| --- | --- |
| 식별·바인딩 | `SecretRef`는 무작위 credential ID와 provider/endpoint fingerprint·계정 별칭·key generation만 가짐. target은 앱 namespace와 ID로 구성하며 키·이메일·endpoint query를 이름에 넣지 않음 |
| 저장 유형·지속성 | BYOK는 `CRED_TYPE_GENERIC`, `CRED_PERSIST_LOCAL_MACHINE` 제안. 여기서 LOCAL_MACHINE은 동일 PC의 동일 사용자의 후속 로그온에서 보이는 의미이며 모든 사용자 공유가 아님. enterprise 로밍은 기본 사용하지 않음. [CREDENTIALW 정의](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw) |
| 인터페이스 | `put(binding, secret) → SecretRef`, `read_for_request(ref, permit) → 제한 수명 secret`, `delete(ref) → Deleted/Absent/Error`. `read_for_request`는 현재 grant·endpoint·key generation을 재검사하고 원문을 작업 DB에 넘기지 않음 |
| 원자성 한계 | Credential Manager와 SQLite 간 단일 트랜잭션을 가정하지 않음. 새 키 기록·읽기 확인 후 참조를 교체하고 이전 키를 정리. 중단 시 참조 없는 앱 소유 credential만 확인 후 정리; 다른 앱 항목을 열거·삭제하지 않음 |
| 저장 실패 | `KEYSTORE_UNAVAILABLE`, `KEY_TOO_LARGE`, `KEY_WRITE_FAILED` 등을 비밀 없는 코드로 표시. 일반 파일·SQLite·환경 변수·레지스트리 평문·소스 설정으로 자동 fallback 금지. 키 저장 실패를 성공으로 표시하지 않음 |
| 읽기 실패 | 누락·접근 실패·유효 로그온 세션 부재를 구분하고 외부 작업만 중단. 키 재입력 경로 제공. 네트워크 오류를 고치려고 키를 로그에 출력하지 않음 |
| 삭제 | 앱 저장소의 삭제와 제공업체 키 폐기는 별개. 존재하지 않음은 멱등 성공으로 처리, 실제 접근 실패는 재시도 가능 상태. API 근거: [CredDeleteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-creddeletew) |
| 메모리·프로세스 | 필요한 순간에만 읽고 수명을 최소화. UI 재표시·clipboard·명령행 인자·자식 환경·임시 파일로 전달하지 않음. 고수준 런타임의 문자열 복사·GC 때문에 완전한 zeroization을 보장하지 않음 |
| export·백업 | 일반 설정/프로젝트/지원 자료에는 credential 참조도 기본 제외. 복원 후 `KEY_REQUIRED`로 표시하고 사용자가 새로 연결. 키 문자열의 일부를 마스킹 표시하는 대신 사용자 지정 별칭 사용 |

Credential Manager 장애, 키 인증 실패, 키 교체·삭제 중 AI 요청과의 경합을 QA-V02에서 시험한다. 동일 사용자 악성 프로세스가 비밀을 읽지 못한다고 약속하지 않는다. 서명 키는 CI의 별도 보호 저장소와 배포 권한 계약을 쓰며 사용자 BYOK 저장소에 섞지 않는다.

## 6. SEC-04: retention/delete와 복구 충돌 해결

### 6.1 보존 기본안과 소유권

원본 불변은 보존 중 내용 변경을 금지한다는 뜻으로 해석하는 안을 제안하며 사용자의 명시적 삭제를 막는 영구 보관 정책으로 확대하지 않는다. 자동 원본 삭제는 기본 꺼짐을 권고한다. 사용자가 보존 기간을 설정하면 적용 대상·예외·기존 자료 영향과 되돌릴 수 없는 시점을 먼저 고지한다. 공간 부족이 임의 원본 삭제의 근거가 되지 않는다.

| 대상 | 제안 기본 정책 | 삭제·복구 조건 |
| --- | --- | --- |
| 원본 트랙·확정 청크·manifest | 사용자가 삭제하거나 명시적 보존 기간을 설정할 때까지 보존 | 캡처 중 파일 삭제 금지. 기본 UX는 명시적 `녹음 중지 후 삭제`. 종료 후 삭제 예약은 스케줄·취소 계약 확정 전 미지원 제안 |
| 전사·요약·검색 인덱스·편집 이력 | 원본과 연결된 파생 자료로 보존, 별도 파생 자료 삭제 제공 | 전체 세션 삭제 시 일괄 대상. 파생 자료만 삭제할 때 재생성 작업·그 권한도 함께 취소 |
| 미완료 청크·재개용 파일 | 복구 판정이 끝날 때까지 보호 | 일반 임시 폴더 청소 대상으로 취급하지 않음. 삭제 의도 기록이 있으면 복구하지 않음 |
| 작업 임시 파일·실패한 다운로드 | 상한·명시된 TTL 적용 | 활성 lease·재개 필요성 확인 후 정리. 활성 원본·확정 청크와 디렉터리 분리 |
| 로그·감사 기록·지원 ZIP | SEC-06의 제한된 기간·크기 | 삭제 완료 뒤 내용·경로 제거, 최소 삭제 의도 ID·상태만 보유 |
| 외부 export·OS 백업·동기화 사본·원격 API 데이터 | 앱 내부 보존과 별개 | 앱이 전부 지운다고 표시하지 않음. 사본 위치와 원격 삭제 가능 여부 안내 |

### 6.2 삭제 상태와 crash 일관성

제안 상태는 `DELETE_REQUESTED → DELETE_PENDING → DELETED_LOCAL`과 재시도 가능한 `DELETE_FAILED`다. 이 상태들은 녹음 세션·AI 작업 상태와 별도다.

1. 사용자 대상·범위를 확인하고 내용 없는 tombstone(`session_id`, `deletion_generation`, 요청 시각, 대상 범위, 진행 상태)을 먼저 영속화한다. 이 기록에 실패하면 파괴적 삭제를 시작하지 않고 실패를 표시한다. DB와 파일 삭제의 동시 원자성을 가정하지 않는다.
2. session generation을 증가시키고 새 전사·요약·export·전송·재개를 차단한다. 실행 중 AI/전송/export에는 취소를 요청하고 활성 캡처는 사용자가 승인한 중지 절차를 수행한다. writer 중지 확인 전 파일을 제거하지 않는다. worker의 늦은 결과는 generation 검사에서 게시를 거부한다.
3. 파일 핸들·작업 lease가 정리된 대상부터 파생 파일, 원본, 인덱스, DB 본문·이력, 앱 관리 임시 파일을 멱등 삭제한다. 다른 세션의 파일·중복 콘텐츠 공유 참조를 지우지 않도록 소유권을 검사한다. 공유 원본 저장은 참조 계산 계약이 마련되기 전 도입하지 않는 안을 권고한다.
4. 파일 잠김·권한 실패·디스크 오류는 남은 대상 수와 코드로 `DELETE_PENDING/FAILED`에 기록한다. 재시작 시 다시 시도하며 휴지통 이동을 영구 삭제 완료로 표시하지 않는다. 삭제 진행중에는 검색·미리보기·지원 묶음에서 제외한다.
5. 복구 스캔은 tombstone을 먼저 확인한다. 있으면 미완료 청크·고아 파일을 세션으로 재등록하지 않는다. 삭제 기록 저장소가 손상되어 의도를 확인할 수 없으면 자동 복구/게시를 보류하고 사용자 판단을 요청한다. 새로운 복구 사본이 생겨도 기존 grant·SecretRef를 복원하지 않는다.
6. 관리 범위의 대상이 없어졌음을 확인한 뒤 `DELETED_LOCAL`로 표시한다. 최소 tombstone은 해당 라이브러리 수명 동안 자동 만료하지 않는 안을 제안한다. 앱 데이터 전체 삭제로 이 기록까지 지우면 오래된 외부 사본의 삭제 이력을 확인할 수 없음을 알린다. 오래된 전체 백업이 tombstone까지 되돌리는 문제는 앱 단독으로 해결했다고 주장하지 않으며 복원 시 자동 작업·외부 동의를 비활성화한다. 최종 tombstone 보존 기간은 D00의 열린 결정이다.

`DELETED_LOCAL`은 앱이 관리하는 활성 파일·색인·참조를 제거한 논리적 삭제 완료다. 디스크의 모든 물리 흔적 제거를 뜻하지 않는다. SQLite WAL에는 추가 파일이 존재하며, `secure_delete`만으로 일부 가상 테이블의 잔재까지 제거된다고 보장할 수 없다. 근거: [SQLite WAL](https://www.sqlite.org/wal.html), [secure_delete 제약](https://www.sqlite.org/pragma.html#pragma_secure_delete). 실제 SQLite 버전·journal·FTS 사용 여부에 맞춘 checkpoint/정리 절차를 별도 검증해야 한다. 운영 중 WAL 파일을 임의 삭제하는 방식은 금지한다.

SSD·OS 백업·동기화·pagefile·외부 사본까지 포함한 안전한 물리 삭제나 cryptographic erase는 현 설계가 보증하지 않는다. 암호화 저장을 추가하려면 미디어·DB·임시 파일·백업·키 회수의 전체 수명과 복구 손실을 함께 결정해야 한다. 보존 삭제와 전원 장애 내구성은 다른 계약이며 어느 쪽도 시험 없이 보장하지 않는다.

## 7. SEC-05: export path·콘텐츠 보안 계약

내보내기 입력은 선택된 세션/파생 버전, 허용 포맷, 사용자 지정 목적 디렉터리, 충돌 처리 옵션이다. 시작 시 고정 artifact 목록의 읽기 lease와 deletion generation을 얻고 최종 게시 직전 삭제 세대·취소 상태를 같은 게시 경계에서 재검사한다. 삭제가 먼저 확정되면 새 export를 완료로 게시하지 않으며 앱이 관리하는 staging만 정리한다. 사용자 삭제는 reader 해제를 기다리고 무한 대기는 진행 상태로 표시한다. 녹음 원본 경로·앱 설정·credential 저장 영역을 내보내기로 덮어쓰지 않는다. 출력 manifest에는 선택된 산출물·포맷·출처 버전·무결성 해시만 포함하며 키·동의 grant·절대 원본 경로·불필요한 장치/사용자 식별자는 포함하지 않는다.

| 위험 | 제안 처리 | 실패/수락 조건 |
| --- | --- | --- |

## 8. SEC-06: 로그·감사·support bundle

로그는 기본 구조화 allowlist만 저장한다. 허용안은 이벤트 코드, 앱/스키마 버전, 임의 작업 ID, 상태 전이, 지속시간·큐 길이·유실 프레임 수, 비밀 없는 OS 오류 코드다. 원문 음성·전사·요약·prompt, 인증 헤더·키, 전체 URL/query, 요청/응답 본문, 사용자 경로·제목·참석자·장치 고유 ID는 금지한다. 감사 기록도 같은 규칙을 따르며 전체 내용을 남기는 편집 이력과 보존 위치·삭제 대상을 구분한다.

예외 객체의 `repr`·SDK 디버그·HTTP wire log·stderr를 그대로 영속화하지 않는다. 사후 정규식 마스킹만으로 해결하지 않고 수집 단계에서 제거한다. 외부 서버 오류 문구도 본문을 재반사할 수 있어 내부 코드로 변환한다. 환경 변수 전체 덤프·메모리 덤프·GPU/크래시 덤프는 기본 수집하지 않는다. OS 자체 덤프·보안 제품 로그는 앱 통제 한계로 고지한다.

지원 자료는 `생성 → 파일별 내용/크기 미리보기 → 로컬 저장 → 사용자의 별도 공유` 흐름을 제안한다. 프로젝트 폴더를 재귀 압축하지 않는다. 최소 앱 버전·오류 코드·비식별 집계만 포함하고, media/DB/WAL/환경·키·프로젝트 경로는 기본 제외한다. 추가 원본 첨부가 꼭 필요한 경우에는 별도 파일 선택·민감 정보 고지·공유 동의가 필요하며 현 기본 지원 묶음과 구분한다. 자동 지원 업로드 기능은 기본 제공하지 않는다.

생성 ZIP과 그 임시 파일에도 같은 ACL·경로·보존 정책을 적용한다. 삭제 대상 자료나 철회한 추가 첨부 권한으로 새 묶음을 생성하지 않는다. API 동의 철회가 비식별 진단의 로컬 생성까지 막는 의미는 아니다. 이미 사용자가 복사·공유한 묶음을 회수한다고 주장하지 않는다. QA canary는 가짜 키·식별 텍스트·경로를 써서 UTF-8/UTF-16·URL encoding·압축 내부를 검사한다. canary 미검출은 해당 시나리오의 증거이며 임의 데이터 비유출의 수학적 증명은 아니다.

## 9. SEC-07: 다운로드 supply chain·SBOM·라이선스

### 9.1 모델·바이너리 다운로드 계약

다운로드 전 이름, 배포자·origin/CDN, 고정 version/revision, 크기/디스크 예산, digest, 라이선스·제약, 저장 위치, 실행 코드 포함 여부를 표시한다. 첫 실행·모델 목록 조회·로컬 전사 시작이 다운로드를 암묵적으로 승인하지 않는다. 모델과 화자 구분 자산의 다운로드를 별개로 다룬다.

신뢰한 릴리스 manifest의 digest와 HTTPS를 함께 사용한다. 같은 변조 가능한 서버에서 파일과 해시를 동시에 받는 것만으로 출처를 증명했다고 보지 않는다. 서명/attestation이 있는 배포는 trust root·검증 방법·키 회전·폐기 규칙을 확인하고, 없는 경우 출처 검토·고정 digest의 한계를 기록한다. `latest`를 재현 가능한 식별자로 사용하지 않는다.

부분 파일은 비실행 격리 디렉터리에 쓰고 범위·크기·digest 확인 뒤 게시한다. resume은 동일 revision과 서버 객체임을 확인할 수 있을 때만 한다. 취소·checksum 실패·서명 불일치·경로 이탈·크기 초과 때 실행/로딩을 막고 상태와 삭제/재시도 선택을 제공한다. redirect/CDN은 manifest에서 승인된 목적지만 허용하며 BYOK 인증 헤더를 전달하지 않는다. 모델 서버용 별도 토큰이 필요하면 그 토큰도 Credential Manager와 endpoint 바인딩 대상으로 취급한다.

가중치 로드 시 pickle·임의 remote code·설치 script 등 코드 실행을 유발하는 경로는 기본 차단한다. 포맷 이름만으로 안전을 보장하지 않고 실제 로더 버전과 의존성을 검토한다. 오프라인 import도 같은 검사·라이선스 표시가 필요하다. 모델 삭제 시 공유 참조와 실행 lease를 확인하고 원본 녹음은 건드리지 않는다. 업데이트의 무결성 실패를 이유로 검증되지 않은 이전 바이너리를 자동 실행하지 않으며 롤백은 승인된 digest로만 한다.

### 9.2 SBOM과 재배포 검토

빌드별 SBOM 제안 필드는 component ID, 이름·버전·revision, package URL/출처, 실제 배포 파일 digest, dependency 관계, runtime/build-only 구분, license declared/concluded, 원문 license/NOTICE 위치, 변경 여부, 검토자·확인일, 취약점/예외 기록이다. SPDX 또는 CycloneDX의 채택 버전은 D00이 정한다. SBOM은 목록 교환 형식이며 적법성이나 취약점 부재 인증이 아니다. 참고: [SPDX 공식 개요](https://spdx.dev/learn/overview/).

| 범주 | 필수 조사 단위 | 출고 차단 조건 |
| --- | --- | --- |
| 앱 코드·기존 VoiceLocal | 파일별 출처·저작권·변경 사항·LICENSE/NOTICE, 원본 제공 이후 차이 | 현재 루트 Apache 문구를 미제공 원본·제3자 코드 전체의 허가로 간주함 |
| Python·STT·추론 패키지 | 정확한 wheel/소스·전이 의존성·native DLL·런타임·패치 | 버전·배포 파일·license 근거 누락, 불명확한 재배포 의무 |
| 모델·tokenizer·VAD·화자 자산 | 코드와 가중치·변환본 각각의 model card·license·사용/재배포·상업/지역/용도 제한 | 모델 카드 표시만 있고 실제 license 미확인, 가중치를 코드 license로 판단 |
| UI | PySide6·Shiboken·Qt의 실제 모듈/플러그인, 폰트·아이콘·번역·테마 | 선택 license와 배포 방식에 필요한 고지·소스/교체 관련 검토 누락 |
| 바이너리·codec·설치 도구 | 패키징 도구, 오디오/변환 DLL, 선택적 FFmpeg, GPU runtime·드라이버 배포물 | 빌드 옵션·정적/동적 결합·번들 파일별 조건 미확인. 설치된 드라이버와 앱 번들 구분 누락 |
| 데이터·서비스 | 평가 음성의 사용 허가, API 약관·지역·보관·과금 정책 | 무허가 시험 데이터, 확인되지 않은 정책을 무보관/학습 제외로 표시 |

Qt for Python 공식 문서는 Community(LGPLv3/GPLv3)와 Commercial 배포를 구분하고 제3자 라이선스를 별도 열거한다. 따라서 `PySide6 사용 = Apache 호환 검토 완료`로 판단하지 않는다. 선택 모듈·배포물·버전별 조건 및 고지·소스 제공·사용자 교체 관련 의무의 적용은 실제 패키징안을 근거로 검토한다. 근거: [Qt for Python 배포 구분](https://doc.qt.io/qtforpython-6/commercial/index.html), [제3자 라이선스 목록](https://doc.qt.io/qtforpython-6/licenses.html).

빌드 CI에서는 잠금 버전·해시, 고정 빌드 환경, 최소 권한 토큰, 외부 PR의 비밀 접근 차단, 보존된 provenance를 제안한다. 서명 대상 digest와 시험·SBOM 대상 digest가 같아야 한다. 서명은 무해성·백신 경고 없음의 증거가 아니며 코드 서명 제공 방식은 열린 결정이다. SLSA는 소스/빌드/배포의 무결성 위협을 정리한 참고 틀로만 사용하며 특정 SLSA 수준을 달성했다고 주장하지 않는다. 참고: [SLSA supply chain threats](https://slsa.dev/spec/v1.2/threats-overview).

미확인 라이선스·필수 NOTICE 누락·검토되지 않은 재배포 제한은 출고 차단이다. 이를 제외한 보안 취약점은 실제 도달성·영향·완화·수정 계획을 기록하며 고위험 예외를 묵인하지 않는다. 도구의 license scan·CVE scan 성공만으로 수동 검토를 대체하지 않는다.

## 10. QA·DevOps·릴리스 관점: 검증 계약과 제안 예산

### 10.1 증거와 판정 규칙

현재 모든 아래 제품 시험은 **NOT_RUN**이다. 문서 작성·공식 문서 확인을 제품 시험 PASS로 바꾸지 않는다. 미래 결과 레코드에는 시험 ID, 요구/SEC ID, commit·배포물 digest, OS build·하드웨어/드라이버·전원 설정, 모델 digest·어댑터 버전, 입력 seed/허가, 절차·fault 주입점, 기대/실측·단위·시계 기준, 반복 수·분포·최악값, 증거 경로, 결과와 한계를 남긴다. 결과 상태는 `PASS/FAIL/NOT_RUN/BLOCKED/NOT_APPLICABLE`로 구분하고 N/A에는 기능 제외 근거를 적는다.

원본 무결성은 트랙별 frame count·format·chunk sequence·checksum·타임스탬프/명시된 gap과 비교한다. 입력 frame 중 저장·명시 유실·진행중인 frame의 회계가 맞아야 한다. OS가 전달하지 않은 frame까지 관측했다고 주장하지 않으며 loopback 무음과 장치 실패를 구분한다. 정렬된 믹스의 오차는 원본 시간 수정과 구분한다.

프로세스 강제 종료, OS crash, VM 전원 차단, 물리 전원 손실은 다른 fault다. 확정·저장 완료·flush 요청·안정 저장에 대한 D02의 내구성 정의를 참조해야 하며 VM 성공을 물리 디스크 전원 장애 보장으로 확대하지 않는다. 복구는 확정 청크 재구성과 중단 중 새 음성의 재생성이 다르다.

### 10.2 수치 목표: 전부 검증 전 제안 예산

## 11. P0~P3 수락 게이트와 릴리스 정책

P0~P3는 [설계 입력](../design-input-v1.md)의 범위를 따른 검토 제안이며 release version이나 일정 약속이 아니다. 보안 통제는 기능이 처음 도입되는 시점부터 적용한다. 예를 들어 P2의 클라우드는 그때 SEC-01을 추가하면 되지만, P0의 로그·export에는 이미 비밀/경로 보호가 필요하다. P1의 다운로드도 P2의 배포 CI 완성을 기다리지 않고 SEC-07을 만족해야 한다.

공통 출고 차단 사유는 무동의 전송·비밀 유출·원본 훼손·잘못된 성공 표시·삭제 후 자동 부활·경계 밖 파일 변경·미확인 필수 라이선스 의무·미완화 고영향 보안 결함이다. 영향을 받는 선택 기능을 완전히 제외하고 제외 증거를 남기는 방법은 가능하지만 알려진 위반을 문서 경고만으로 PASS 처리하지 않는다. 이 배포 차단의 심각도는 P0~P3 기능 우선순위와 다른 축이다.

미래 CI 단계안은 (1) 변경/비밀·schema 검사, (2) 결정적 합성·fault 시험, (3) 고정 환경 패키징·SBOM·license 검토, (4) 깨끗한 VM smoke, (5) 해당 변경의 실장비/선택 cloud 시험, (6) artifact digest·서명·릴리스 증거 검토다. 클라우드 비용·서명 키·고위험 장비 시험은 격리된 신뢰 환경으로 분리한다. 네트워크/계정/장비 부재에 따른 BLOCKED를 반복 재시도 성공으로 숨기지 않는다.

릴리스 증거 묶음에는 범위와 제외 기능, 요구사항→시험 추적, 채택 예산과 실측, 지원 OS/장비 표, 미해결 결함·제약, 정확한 binary/model digest·SBOM·NOTICE·provenance·서명 판정, 설치/롤백/복구/삭제 결과를 넣는다. 일반 공개 배포에는 선언한 기능의 게이트를 만족해야 하고, 제한된 내부 preview라면 미검증 범위와 사용 가능 기능을 명시한다. 문서 설계 완료는 어느 제품 게이트도 통과시킨 것이 아니다.

현재 문서 단계에서는 D00이 요구사항 누락·문서 링크·계약 충돌·비밀 노출·수정 범위를 최종 검사한다. 그 뒤 대상 브랜치/remote·무관한 변경을 확인해 필요한 문서만 stage/commit/push하고 원격 참조 일치를 확인한다. **D04는 push하지 않으며 push 완료를 보고하지 않는다.**
