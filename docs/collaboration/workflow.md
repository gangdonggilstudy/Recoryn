# Recoryn 세션 협업 규칙

## 현재 단계와 책임

현재 단계는 설계 작성 및 전문가 리뷰다. 사용자 요청에 따라 메인 세션이 오케스트레이터를 맡고, 기존 Recoryn 작업 세션에 문서 검토를 배정한다. 구현이나 하드웨어 시험을 완료했다고 표시하지 않는다.

오케스트레이터는 요구사항과 통합 설계의 일관성, 배정, 충돌 해결, 리뷰 종결, 최종 검사, commit 및 push를 책임진다. 작업자는 검토 기준에 따른 설계, 근거, 실패 시나리오와 검증 가능한 수락 기준을 제공한다. 전문가 페르소나는 실제 전문 자격이나 제품 인증을 뜻하지 않는다.

## 파일 소유권과 변경 절차

배정표에 배정 ID, 역할, 소유 파일, 의존성, 수락 기준, 상태를 기록한다. 원칙은 파일 하나에 활성 작성자 한 명이다. 다른 파일의 문제는 해당 파일을 직접 고치지 않고 경로와 수정 제안을 보고한다. 공용 계약 변경은 오케스트레이터가 영향 범위를 정리한 뒤 새 배정으로 전달한다.

작업자는 배정 문서만 수정하며 Git 인덱스나 브랜치를 변경하지 않는다. 공용 작업 디렉터리에서는 자신의 diff와 전체 diff를 구분하고, 타인의 변경을 되돌리지 않는다. 별도 worktree가 필요한 경우 오케스트레이터가 사용자 범위 내에서 명시적으로 준비한 후 경로와 브랜치를 배정한다.

작업 상태는 `QUEUED → ASSIGNED → WORKING → REVIEW_READY → INTEGRATED → VERIFIED`다. 막힘은 `BLOCKED`와 원인, 해소 조건을 기록한다. 재작업은 `REVIEW_READY → WORKING`으로 돌아간다. `VERIFIED`는 해당 배정의 검증만 의미하며 제품 전체 검증을 뜻하지 않는다.

## 지시와 완료 보고

지시는 배정 ID, 역할, 목적, 필독 문서, 쓰기 허용 파일, 제외 범위, 필요한 산출물과 수락 기준을 포함한다. 초기 prompt에는 결과를 채팅에 요약하도록 하고, 파일은 배정된 실제 설계 산출물만 작성한다. 출력 조회로 완료 보고를 복원할 수 없는 경우에만 Herdr 지침의 임시 파일 fallback을 사용한다.

완료 보고에는 변경 파일, 핵심 결정, 가정, 미해결 질문, 검증 방법과 결과를 포함한다. 코드가 없는 문서 작업에는 의미 없는 구현 테스트를 추가하지 않는다. 오케스트레이터는 요구사항 추적, 문서 링크, 용어, 상태 전이, 파일 경계, 개인정보 및 복구 정책의 충돌을 검사한다. 중대한 미해결 항목은 완료로 닫지 않는다.

시험 계층과 독립 승인 기준은 [품질 및 교차 검증 체계](../quality-system.md)를 따른다. 작성자는 자체 검증 결과를 제출하고, 다른 세션은 위험과 경계를 중심으로 교차 검토한다. 수정자는 발견 사항을 단독 종결하지 않으며 검토자가 재확인한다. 교차 검토 기록은 `docs/reviews/`에 남기고 오케스트레이터가 종결 상태를 배정표와 연결한다.

## Herdr 운용

같은 서버의 Recoryn 워크스페이스만 다룬다. `HERDR_ENV=1` 확인 후 CLI 도움말을 읽고 workspace, tab, pane과 agent 목록에서 ID를 찾는다. 현재 작업의 환경 변수 ID가 오래되었을 수 있으므로 실제 목록과 대조한다. ID는 위치나 번호로 추측하지 않는다.

대상 상태와 최근 출력을 확인한 뒤 agent prompt로 지시한다. timeout과 stalled는 미전송을 뜻하지 않는다. 먼저 get/read 후 재시도를 판단한다. `blocked`에서는 UI를 읽고 승인이나 질문을 사용자의 동의 없이 대신 처리하지 않는다. 상태가 idle이어도 완료 결과를 읽어 확인한다. 오케스트레이터는 장시간 진행 중 주기적으로 사용자에게 진척을 알린다.

새 pane, 탭, workspace 또는 프로세스를 만드는 일은 필요성과 권한을 확인한 뒤 진행한다. 기존 세션을 임의 종료하거나 Herdr 서버를 재시작하지 않는다. 작업자의 추가 위임은 자동 허용되지 않는다.

## 최종 검증과 푸시

사용자는 최종 검증 후 푸시를 오케스트레이터가 수행하도록 승인했다. 작업자는 push하지 않는다. 오케스트레이터는 다음을 순서대로 수행한다.

1. 배정 산출물과 완료 보고를 읽고 충돌 및 보류 항목을 정리한다.
2. 변경 diff와 필요한 검사 결과를 확인한다. 문서 전용 단계에서는 링크, 요구사항 누락, 명세 모순과 비밀 노출을 검사한다.
3. 대상 브랜치와 remote를 확인하고 이번 작업 파일만 stage한다. 무관한 변경이 있으면 남겨 둔다.
4. 검증 범위와 남은 제한을 담아 commit한다. 이력이 갈라지거나 비정상 원격 변경이 있으면 강제 push하지 않고 조정한다.
5. 원격으로 push하고 성공 응답 및 로컬 commit과 원격 참조의 일치를 확인한 뒤 보고한다.

권한, 인증, 네트워크 문제는 실제 실패 근거와 함께 보고한다. 필요한 도구 승인 절차를 따르며, 성공하지 않은 push를 완료로 기록하지 않는다.
