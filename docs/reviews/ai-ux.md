# D03 — ML 시스템 및 데스크톱 UX 설계 검토

작성일: 2026-11-14. 상태: **REVIEW_READY / 통합 채택 전 제안**. 관점: ML 시스템 엔지니어, 데스크톱 UX 전문가. 이 문서는 설계 산출물이며 구현·실행·성능·접근성 인증 결과가 아니다.

## 1. 범위, 요구사항과 제안의 구분

근거 문서는 [설계 입력](../design-input-v1.md), [작업 규칙](../collaboration/workflow.md), [배정표](../collaboration/assignments.md), [온보딩](../collaboration/onboarding.md), [루트 규칙](../../AGENTS.md)이다. 읽기 시점에 `docs/architecture-v1.md`, `docs/validation-plan.md`는 없었다. 작성 중인 문서의 결정을 추정하지 않는다. VoiceLocal 소스는 제공되지 않았으며 원본 분석, 마이그레이션, 하드웨어 시험은 수행하지 않았다. 이후 나타나는 다른 작업자의 산출물은 이 검토에서 검증했다고 간주하지 않는다.

**사용자 원칙**은 R01~R06으로 추적한다. 원본 분리 보존, AI 실패와 무관한 녹음, 로컬 전용 기본값, 제공업체·데이터 종류별 외부 전송 동의, 명시적 모델 다운로드, 부분 결과·재개·취소·관측, 비밀의 Credential Manager 보관, 선택적 어댑터가 여기에 해당한다. 설계 입력의 CPU 전환 동의, 전사 초안/정정 구분, 근거 연결, 긴 문서 분할 요약도 유지한다.

**D03 제안**은 아래의 필드명·메서드·상태·정책·수락 기준이다. 실제 라이브러리의 기존 인터페이스라는 뜻이 아니다. 공용 계약 채택과 우선순위 확정은 D00, 저장·작업 상태 통합은 D01, 시간축·복구 경계는 D02, 권한 저장·전송 통제·검증 게이트는 D04와 조정한다. 아래에서 “해야 한다”는 표현은 이 제안을 채택할 때의 구현 의무다. 성능 수치나 모델 품질 목표는 시험 전 확정하지 않는다.

## 2. 선택적 STTProvider / SummaryProvider 계약

### 2.1 로딩과 기능 협상

STT와 요약은 독립 선택이며 각각 `NONE`을 지원한다. Faster-Whisper가 로컬 STT 기본 **후보**이고 Ollama 요약은 선택 사항이다. 녹음 전용 설치와 AI 없이 세션 열기·재생·내보내기가 가능해야 한다. UI 초기화나 캡처 시작이 모델 import, 서버 연결, GPU 초기화, 모델 설치를 기다리면 안 된다. 누락된 선택 의존성은 해당 어댑터만 `UNAVAILABLE`로 만든다.

`describe()`는 설치된 어댑터의 정적 설명을 반환하고 네트워크를 사용하지 않는다. `probe(scope)`는 승인된 목적지에 한해서 설치·모델·런타임 정보를 조회하며 녹음/전사를 전송하지 않는다. 자동 공개 서버 검색이나 외부 연결 시험은 하지 않는다. 설명은 `DECLARED`, 실제 조회 결과는 `OBSERVED`, 검증되지 않은 항목은 `UNKNOWN`으로 구분한다. 정적 선언만으로 전송 권한을 부여하지 않는다.

| 계약 | 필수 필드 및 의미 |
| --- | --- |
| ProviderDescriptor | `contract_version`, `provider_id`, `adapter_version`, `kind=stt/summary`, 지원 여부와 미지원 이유. 표시 이름으로 권한을 식별하지 않는다. |
| ExecutionDescriptor | `model_id`, 가능하면 불변 `model_digest/revision`, `runtime_version`, `endpoint_id`, `transport_location=embedded/loopback/remote/unknown`, `execution_location=local/remote/unknown`, 실제 처리자 목록, 데이터 종류, 로컬 실행 검증 근거. 변경 시 실행 계획을 다시 만든다. |
| STTCapabilities | 지원 언어/자동 언어 감지, `batch`, `streaming` 또는 `windowed_batch`, segment/word 타임스탬프, 화자 구분, 입력 포맷·최대 바이트/길이·채널 수, VAD 적용 주체, 취소·체크포인트 지원. `unknown`을 `true`로 승격하지 않는다. |
| SummaryCapabilities | 실제 사용 가능한 입력/출력 한도, 토크나이저 식별자 또는 추정 방식, 구조화 출력 지원 여부, 스트리밍·취소·체크포인트 지원, 과금 단위. 어댑터마다 확인한다. |
| Estimate | `amount/range`, `currency`, 가격표 출처·확인 시점, 입력 단위, 가정, `upper_bound_known`, 불확실성. 시간 예상은 측정 근거가 없으면 “계산 전”이다. |
| ExecutionPlan | 입력 해시·revision, 모델/설정·전처리 해시, 목적지/데이터 종류, 장치 정책, 비용 예약, 재시도 한도, 권한 버전. 사용자에게 보여준 계획과 실제 dispatch가 일치해야 한다. |

선택한 기능이 미지원이면 입력 일부를 몰래 버리거나 다른 제공업체를 호출하지 않는다. 예를 들어 word 타임스탬프가 없으면 segment 단위 이동을 제공하고 정확도를 “구간 단위”로 표시한다. streaming 미지원 어댑터의 반복 batch는 “구간별 초안”으로 표시한다. 화자 구분은 선택적 별도 모델·설치 권한이 필요하며 트랙명과 실제 화자 신원을 동일시하지 않는다.

### 2.2 요청, 결과, 오류

다음 표기는 구현용 중립 의사 계약이다. 프로세스 간 통신과 직렬화 형식은 D01이 확정한다.

```text
STTProvider.transcribe(STTRequest, JobContext) -> EventStream[STTEvent]
SummaryProvider.summarize(SummaryRequest, JobContext) -> EventStream[SummaryEvent]

JobContext = job_id, attempt_id, idempotency_key, cancel_token,
             deadline, permission_snapshot_id, budget_reservation_id
STTRequest = immutable_media_refs, track_ids, source_ranges,
             timeline_mapping_revision, language_policy, vad_policy,
             model_settings, execution_plan_id, checkpoint_ref?
SummaryRequest = transcript_revision_id, transcript_hash, allowed_segment_ids,
                 template_id/version, output_language, context_plan,
                 model_settings, execution_plan_id, checkpoint_ref?
Event = event_id, job_id, attempt_id, sequence, type, payload_ref
type = progress | partial_checkpoint | completed | failed | cancelled
Error = code, stage, retryable, outcome_known, safe_message,
        preserved_artifacts, next_actions, diagnostic_id
```

- `transcribe()`는 확정 청크 또는 별도 파생 미디어 참조만 받는다. 캡처 장치나 원본 쓰기 핸들에 접근하지 않는다. 클라우드 어댑터는 승인된 범위의 업로드 payload만 받으며 프로젝트 폴더 전체를 읽지 않는다.
- `summarize()`는 명시적으로 선택한 불변 전사 revision만 읽는다. 음성은 기본 입력에 없으며 오디오 업로드 권한도 요구하지 않는다. 중간 요약·프롬프트·선택 구간도 전송 데이터 목록에 포함한다. BYOK 값은 요청 본문/이벤트에 넣지 않고 보안 계층의 핸들로 참조한다.
- 이벤트는 중복·지연·역순 도착할 수 있다고 설계한다. 소비자는 `event_id`와 attempt/sequence로 중복을 무시한다. `progress`에는 단위, 완료량, 전체량 또는 `unknown`을 명시한다. 생성 토큰 수를 사실성이나 완료율로 변환하지 않는다.
- provider 완료는 앱 게시 완료가 아니다. 결과 구조·해시·시간 범위·근거를 검증하고 산출물 및 revision 메타데이터를 일관되게 게시한 뒤 UI의 사용 가능한 결과를 바꾼다. 게시 실패 시 직전 정상 revision을 유지하고 고아 산출물은 복구 대상으로 남긴다.
- 같은 논리 작업의 재시도는 `job_id`를 유지하고 `attempt_id`를 새로 만든다. idempotency key는 앱 내부 중복 게시 방지용이며 제공업체의 중복 과금 방지를 보장하지 않는다. 외부 API의 멱등성 기능은 어댑터별 검증 전 사용을 전제하지 않는다.
- 체크포인트는 입력 해시, 모델/설정/템플릿, 계획, 완료 범위와 연결한다. 모두 일치해야 이어서 계산한다. 제공업체가 추론 내부 재개를 지원하지 않으면 확정 단위부터 다시 실행한다. 새 모델·수정 전사로는 새 논리 작업을 만든다.

오류 코드는 최소 `DEPENDENCY_MISSING`, `MODEL_MISSING`, `CAPABILITY_UNSUPPORTED`, `CONSENT_REQUIRED`, `CONSENT_REVOKED`, `AUTH_REQUIRED`, `INPUT_INVALID`, `CONTEXT_LIMIT`, `RESOURCE_EXHAUSTED`, `BUDGET_BLOCKED`, `RATE_LIMITED`, `NETWORK_TIMEOUT`, `REMOTE_OUTCOME_UNKNOWN`, `RESULT_INVALID`, `PUBLISH_FAILED`, `CANCELLED`를 구분한다. 오류·진단에는 비밀, 음성, 전사 본문을 넣지 않는다. 취소 요청은 원격 실행의 중단·삭제·환불 성공을 의미하지 않는다.

## 3. 불변 전사 revision과 안정적인 근거

### 3.1 세 종류의 전사

| 종류 | 생성과 표시 | 게시 규칙 |
| --- | --- | --- |
| `draft` | 실시간/구간별 인식의 초안. “임시 전사 · 변경될 수 있음”, 처리 지연·미처리 범위를 함께 표시한다. | UI의 아직 저장하지 않은 버퍼와 구분한다. 저장한 각 snapshot은 새 revision이며 이전 snapshot을 수정하지 않는다. 기본 요약 입력에서 제외한다. |
| `corrected` | 확정 미디어를 대상으로 한 종료 후 재전사·정렬 결과. “후처리 전사 · 자동 생성”으로 표시한다. | 모델이 더 정확하다는 보장이 아니다. 처리 완료 범위와 공백을 저장하고 기본 요약 입력 후보로 삼는다. LLM의 내용 보완은 자동 정정으로 합치지 않는다. |
| `edited` | 사용자가 corrected 또는 다른 revision을 편집한 파생본. “사용자 편집본”과 편집 이력을 표시한다. | 저장마다 새 revision과 부모 참조를 만든다. 원문은 유지한다. 생성형 정정 제안은 별도 제안으로 보여주고 사용자가 수락한 변경에 출처를 기록한다. |

`TranscriptRevision` 필수 값은 `schema_version`, `session_id`, `revision_id`, `kind`, `parent_revision_ids`, `created_at`, `producer`(모델·어댑터·설정 또는 사용자), `media_manifest_revision/hash`, `timeline_mapping_revision`, `content_hash`, `coverage`, `segment_refs`, `completeness=partial/complete`, 실패·미처리 구간이다. `complete`는 계획 범위 처리 완료를 뜻하며 정확성이나 녹음 무손실 보장이 아니다. 세션의 `active_transcript_revision_id`는 가변 선택 포인터로 두고 실제 revision은 변경하지 않는다.

전사 변경 중 이전 revision을 바탕으로 요약이 끝나면 그 요약을 원 revision에 귀속한다. 현재 전사가 바뀌었다는 배지를 표시하고 재요약을 제안한다. 자동 덮어쓰기나 edited 전사의 강제 교체는 금지한다. 동시 편집 저장은 예상 부모 revision을 검사하고 분기/비교를 제공한다. 실행 취소도 새 edited revision을 생성한다.

### 3.2 segment와 시간축 계약

`Segment`는 `(transcript_revision_id, segment_id)`로 식별하며 목록 순번이나 표시 텍스트를 ID로 쓰지 않는다. 한 revision 안의 segment는 불변이다. 재전사 또는 분할·병합은 새 segment와 `derived_from` 다대다 관계를 생성한다. 경계가 바뀌어도 같은 ID를 재사용하지 않는다.

각 segment는 `track_id`, 원본 청크/샘플 범위, `time_start_us/time_end_us`, `timeline_mapping_revision`, 텍스트, 가능한 word 범위, 생성 출처, 불확실성/누락/발화 중첩 표시를 가진다. 시간 범위는 `[start,end)` 정수로 정의한다. 샘플레이트 변환·VAD·드리프트 정렬 후에도 원본으로 역참조 가능한 매핑을 저장한다. 실제 음성의 단어 경계 정밀도는 별도 검증 대상이다. 오디오 결손은 명시적 gap으로 남기며 시간축을 압축해 숨기지 않는다.

`EvidenceRef`는 다음을 포함한다.

```text
revision_id, segment_id, segment_content_hash,
text_span?, track_id, source_sample_ranges,
time_range_us, timeline_mapping_revision
```

범위·해시·revision이 일치하는지 확인한 뒤 저장한다. 시간만 있는 링크, “현재 전사의 12번째 행” 같은 링크는 근거 계약으로 인정하지 않는다. 오래된 요약의 링크는 해당 revision을 열고 원본 음성 구간으로 이동한다. 새로운 revision으로 이동할 때는 “대응 구간 보기”로 별도 표시하고 근거를 조용히 재연결하지 않는다. 사용자 삽입 문장이 실제 음성에 없으면 상속한 구간을 발화 증거로 삼지 않고 `user_assertion`으로 표시한다. 분할·병합 후 구간을 특정할 수 없으면 `unresolved`다.

### 3.3 요약의 주장 단위와 신뢰 표시

요약은 단순 문자열 외에 `SummaryRevision`, `Claim[]`, 입력 coverage를 저장한다. `SummaryRevision`은 원 전사 revision·해시, 모델/템플릿/설정, 중간 결과 계보, 생성 시간, `partial/complete`, 검증 결과를 가진다. `Claim`에는 `claim_id`, 유형(내용/결정/할 일/질문), 본문, `evidence_refs[]`, `basis=transcript/user_assertion/model_inference`, `review_state`와 누락 이유를 둔다. 할 일의 담당자·기한도 각각 근거를 연결하고 없으면 “미지정”으로 남긴다.

- **구조 검증**: 존재하지 않는 segment, 다른 revision, 범위·해시 오류는 `invalid_reference`로 거부한다. 모델이 출력한 ID를 그대로 신뢰하지 않는다. 텍스트 형식 응답도 앱이 schema로 파싱·검증하며 무제한 재생성하지 않는다.
- **내용 검토**: 근거 ID의 존재만으로 의미적 뒷받침을 확인했다고 표시하지 않는다. 초기값은 `unreviewed`; 사람 검토로 `supported/disputed`, 근거 없음은 `unsupported`, 불명확하면 `uncertain`으로 둔다. 선택적 자동 검토는 보조 의견이며 검토 주체를 기록한다.
- UI는 “자동 생성 · 사실 확인 필요”를 요약 상단에 표시하고, “근거 없음”, “해석/추론”, “상충 발언”, “사용자 입력”, “참조 오류”를 주장 옆에 텍스트와 아이콘으로 보여준다. 모델 확률을 사실성 확률처럼 표시하지 않는다.
- 근거 없는 주장을 삭제해 정상 결과처럼 보이게 하지 않는다. 검토 목록에 보존하되 결정/확정 할 일 영역에서는 제외한다. 서로 다른 발언이 충돌하면 양쪽 근거와 미해결 상태를 유지한다.
- Markdown/JSON 등 지원 내보내기에는 revision, 근거와 불확실성 표시를 포함한다. 근거를 보존할 수 없는 형식에는 그 한계를 알리고 확정 사실처럼 내보내지 않는다. 근거 대상이 삭제/손상되면 “근거 사용 불가”로 바뀌며 복원·재검증 없이는 정상 배지를 유지하지 않는다.

## 4. 긴 전사 요약과 VAD 중복 제거

### 4.1 long context 처리

1. 실행 시 전사 revision을 고정한다. 사용자가 edited를 선택하면 사용자 변경과 음성 근거의 구분도 입력에 넣는다. draft 요약을 별도로 허용할 경우 명시적 선택과 “임시 입력” 표시가 필요하다.
2. `입력 토큰 + 시스템/템플릿/schema + 예약 출력 + 안전 여유 <= 검증된 유효 컨텍스트`를 만족하도록 계획한다. 모델 광고 한도, 서버 설정, 앱 설정 중 검증된 한계를 적용한다. 토크나이저가 없으면 보수적 추정과 오차를 표시하고, 안전 범위를 산정할 수 없으면 작업을 보류한다. 조용한 잘림을 허용하지 않는다.
3. segment/주제 경계를 우선 사용하되 큰 segment는 원본 span을 보존해 분할한다. `core_segment_ids`와 `context_segment_ids`를 나누고 겹친 문맥은 이해용으로만 쓴다. 모든 입력 span에 최소 한 개의 핵심 소유 구간을 배정하고 coverage 검사를 한다. 겹침 크기는 모델·언어별 검증 후 정할 설정값이며 고정 초/문자 수를 품질 보장으로 제시하지 않는다.
4. 각 구간은 근거 ID가 붙은 사실·결정·할 일·불확실성·미해결 질문을 구조화한다. 중간 결과가 전사와 원 근거로 연결되는지 검증한다. 음성/전사 내 명령문은 인용 데이터로 취급하며 도구 실행·전송 목적지 변경·권한 부여에 사용하지 않는다.
5. 통합 단계는 유효한 중간 결과와 원 근거 목록을 받는다. 최종 근거는 중간 요약의 ID에서 끝나지 않고 원 전사 segment까지 펼쳐져야 한다. 겹침 때문에 같은 근거·주장이 중복될 때만 병합하고 상충 발언과 서로 다른 시점의 결정은 보존한다. 통합 입력도 한도를 넘으면 동일 규칙으로 추가 계층을 만든다.
6. 일부 구간 실패 시 완료 구간을 체크포인트로 남기고 빠진 범위를 표시한 `partial` 결과를 제공한다. 모든 핵심 범위의 성공·검증이 충족되지 않으면 전체 요약 완료로 표시하지 않는다. 복구는 실패 구간과 영향을 받은 상위 통합만 다시 수행한다.

지원 입력 언어와 출력 언어는 별도 선택이다. 혼합 언어·번역 요약에서도 원문 근거를 유지하며 이름·날짜·숫자·부정문·결정 변경을 별도 평가한다. CER/WER 또는 사람이 평가한 사실성·근거 누락률은 동의된 평가 자료와 조건을 명시해 측정한다. 모델 간 점수를 호환되는 절대 신뢰도로 사용하지 않는다.

### 4.2 VAD, overlap과 반복 발화

VAD는 파생 STT 입력 범위를 고르는 도구다. 원본 청크를 삭제하지 않고 무음 판정 이력·매개변수·버전과 원본 시간 매핑을 남긴다. 앱 VAD와 어댑터 내부 VAD의 적용 주체는 하나로 정한다. 이중 적용이 불가피하면 각 변환을 기록하고 되돌릴 수 있게 하며, 재매핑 검증 전에는 사용하지 않는다. Faster-Whisper 공식 README는 VAD와 word timestamp 예제를 제공하지만 이것이 Recoryn의 스트리밍·정렬 품질을 보장하지는 않는다. [공식 README](https://github.com/SYSTRAN/faster-whisper)

각 입력 window에는 `window_id`, `core_source_range`, `context_source_ranges`와 처리 attempt를 둔다. 같은 작업·설정·원본 범위의 재전송은 idempotency key로 중복 게시를 차단한다. 인접 window의 겹친 단어는 같은 트랙·같은 원본 시간 범위라는 조건 아래 정렬하여 core 소유 구간에 한 번만 게시한다. 불일치하면 합의되지 않은 경계로 표시하고 corrected 단계에서 재처리한다. 문자열만 같다는 이유로 삭제하지 않는다.

예를 들어 동일한 원본 10~12초가 두 window에 들어가면 한 번 게시해야 한다. 실제 10초와 20초에 두 번 말한 “네”, 말 더듬음, 의도적 반복, 다른 화자의 같은 대답은 남겨야 한다. 마이크에 유입된 시스템 음성과 시스템 트랙의 유사 문장은 에코 후보일 뿐 VAD 중복으로 삭제하지 않는다. 교차 트랙 에코 판정은 별도 파생 처리와 평가 대상이며 원본 트랙은 보존한다. VAD false negative가 의심되면 VAD 없이 선택 범위를 재전사하는 동작을 제공한다.

## 5. GPU, CPU와 자원 실패 정책

사용자 장치 정책은 `GPU_ONLY`, `CPU_ONLY`, `GPU_WITH_CPU_FALLBACK_ALLOWED`로 명시한다. 마지막 정책은 CPU 사용 허용을 사용자가 선택했을 때만 저장하며 기본 선택은 꺼진 상태다. GPU 없는 장치에서 CPU 직접 실행도 실행 전 선택을 받는다. CPU 전환 동의는 모델 설치·모델 변경·클라우드 전송을 허용하지 않는다.

- 모델 로드 전 GPU/RAM 관측과 요구량 추정의 시점·불확실성을 기록한다. 메모리 조회 실패를 무한 가용량으로 취급하지 않는다. 예약은 앱 내부 동시 작업 조정이며 다른 프로세스의 소비를 통제하는 보장이 아니다.
- STT와 요약의 무거운 GPU 작업은 기본 직렬화하고 녹음 중에는 STT 초안을 우선한다. 자원 부족 시 요약·AI 초안을 대기시키고 확정 청크 저장은 계속한다. 대기량과 마지막 처리 시각을 표시하며 무제한 메모리 큐를 쌓지 않는다.
- OOM이면 해당 worker/attempt를 실패 처리하고 마지막 확정 결과를 유지한다. 동일 모델·장치에서 batch/context를 줄이는 재시도는 계획된 유한 횟수 안에서만 수행한다. 모델/정밀도 변경은 결과 품질에 영향을 주므로 별도 계획 변경으로 보여준다.
- CPU 허용 시 새 attempt와 실제 장치 표시를 남긴다. 미허용이면 `WAITING_USER`와 “GPU 메모리 부족 · 녹음은 계속 중”을 보여주고 “CPU로 실행 허용”, “모델/작업 설정 변경”, “나중에 재시도”, “AI 작업 취소”를 제공한다. 클라우드 자동 fallback은 하지 않는다.
- 어댑터/서버가 자동 CPU offload를 강제하거나 실제 배치를 사전에 제한할 수 없으면 `GPU_ONLY`를 지원한다고 선언할 수 없다. `strict_device_policy_supported=false/unknown`으로 표시하고 해당 정책에서는 실행을 차단한다. 관측만으로 사전 금지를 구현했다고 주장하지 않는다. Ollama는 CPU/GPU 혼합 배치를 표시할 수 있다고 문서화하지만 서버 버전·설정에 따른 강제 정책 지원은 별도 검증이 필요하다. [Ollama Local FAQ](https://docs.ollama.com/faq)
- worker가 취소를 수용하지 않으면 격리 worker 종료를 검토하되 앱이 소유한 프로세스만 대상으로 한다. 공유 Ollama 서버를 자동 종료하지 않는다. 원격/공유 서버에서는 로컬 대기를 끝내고 실행 결과 불명 상태를 표시한다.

## 6. 모델 설치, 데이터 전송, Ollama 수신 주소 동의

### 6.1 권한은 서로 독립이다

| 동작 | 사용자에게 보여줄 내용 | 허용하지 않는 권한 확장 |
| --- | --- | --- |
| 모델/런타임 다운로드 | 저장소·수신/배포 주체, 모델 ID/버전, 크기 또는 미확인, 저장 위치, 라이선스 확인 상태, 디스크 요구량 | 음성·전사 업로드 동의로 사용하지 않는다. 모델 선택/앱 시작만으로 다운로드하지 않는다. |
| 클라우드 STT | 제공업체·endpoint·실제 처리자, 선택 오디오 트랙/구간, 포맷·길이/크기, 부가 메타데이터, 보존 정책 확인 상태, 예상 비용 | 클라우드 요약 전사 전송을 허용하지 않는다. 불필요한 프로젝트명/로컬 경로는 전송하지 않는다. |
| 클라우드 요약 | 제공업체·endpoint·실제 처리자, 전사 revision·구간, 템플릿/중간 요약·첨부 데이터, 보존 정책 확인 상태, 예상 비용 | 원본 음성 전송, 다른 STT 서비스 호출을 허용하지 않는다. |
| loopback Ollama 요약 활성화 | 정확한 수신 origin, 모델, 보내는 전사 범위, 실제 로컬 실행 확인 상태 | LAN/인터넷 주소, 클라우드 실행 모델, 다른 포트/서버로 자동 확장하지 않는다. |
| CPU fallback | 대상 작업·모델, CPU 전환 범위, 시간/전력 영향은 미측정일 수 있음 | 다운로드나 외부 전송 권한을 부여하지 않는다. |

전송 권한은 `provider_id + endpoint_id/origin + processing_locations + purpose + data_categories + session/range_scope + validity + permission_version`으로 저장한다. 기본은 해당 작업 한 번이며 세션/지속 범위 허용은 사용자가 따로 선택한다. 클라우드 STT 동의가 있어도 요약 동의가 없으면 전사는 생성하되 요약 호출은 하지 않는다. 반대 조합은 로컬 전사만 클라우드 요약으로 보낼 수 있다. BYOK 입력은 인증 설정이며 전송 동의가 아니다.

작업 생성 때와 매 dispatch/재시도 직전에 보안 계층이 권한·목적지·payload 범위를 다시 검증한다. 철회/만료 시 대기 요청을 막고 가능한 진행 중 요청 취소를 시도한다. 이미 전송된 데이터는 회수했다고 표시하지 않는다. 새 제공업체, 주소, 데이터 종류, 처리 위치, 권한 범위를 넘는 입력 변경은 새 동의가 필요하다. 권한 범위 안의 재시도도 비용 제한을 별도로 만족해야 한다.

다운로드 취소 시 부분 파일은 실행 가능한 모델로 등록하지 않는다. 검증된 재개 기능이 있으면 동일 artifact를 재개하고, 없으면 명시적으로 다시 받는다. hash/manifest·라이선스 검증 전 사용 가능으로 표시하지 않는다. 라이브러리의 자동 fetch 경로와 telemetry도 네트워크 정책으로 통제할 수 있는지 구현 시 확인한다. 자동 fetch를 막을 수 없는 어댑터는 로컬 전용 모드에서 사용할 수 없다.

### 6.2 로컬 주소와 로컬 처리의 차이

Ollama 공식 문서는 기본 loopback 바인딩을 설명하며, 로컬 API를 통해 클라우드 모델을 호출하는 예도 제공한다. 따라서 `localhost`와 모델명만으로 외부 전송 없음이라고 판정하지 않는다. [Local FAQ](https://docs.ollama.com/faq), [인증 문서](https://docs.ollama.com/api/authentication)

제안 정책은 다음과 같다.

1. 기본 외부 egress는 닫는다. loopback API도 “이 컴퓨터의 Ollama에 전사 보내기” 활성화 전에는 probe와 payload 전송을 하지 않는다. 활성화는 외부 제공업체 동의와 구별된 로컬 프로세스 전달 권한이다. 미설치 상태에서는 다운로드 안내만 제공한다.
2. 주소는 scheme/host/port를 정규화하고 사용자 정보가 든 URL을 거부한다. `127.0.0.1`/`::1` 및 실제 연결이 loopback인 `localhost`만 로컬 후보로 본다. LAN, VPN, 사용자 정의 DNS 이름은 같은 PC라는 주장만으로 로컬 분류하지 않는다. `0.0.0.0`은 연결 대상에 허용하지 않는다.
3. loopback 호출은 환경 프록시 우회를 명시하고 리다이렉트를 자동 추종하지 않는다. DNS 응답과 실제 연결 주소가 달라지거나 origin이 바뀌면 중단한다. 원격 endpoint는 TLS/서버 검증을 요구하고 실패 시 외부 전송을 보류한다. 사설망도 외부 기기로 분류하며 보안 예외 허용 여부는 D04 결정을 받는다.
4. `transport_location=loopback`과 `execution_location=local/remote/unknown`을 따로 저장한다. 로컬 모델·실행 환경 및 cloud 기능 차단 상태를 검증 가능한 구성으로 확인한 경우에만 “로컬 처리”로 표시한다. 모델 태그 이름만으로 검증하지 않는다. 확인 불가한 서버는 transcript 전송을 막고 설정 확인 또는 확인된 외부 처리자에 대한 별도 동의를 요청한다.
5. 클라우드 모델/중계가 확인되면 loopback 진입점과 실제 클라우드 처리자를 함께 보여주고 **요약용 외부 전송** 동의를 받는다. 처리자를 특정할 수 없으면 광범위한 “모든 외부 서비스 허용”으로 우회하지 않는다. 기능 지원이 확인될 때까지 차단한다.
6. Ollama의 cloud 비활성화 설정은 공식 문서에 있으나 앱이 사용자 서버 설정을 몰래 변경하지 않는다. 앱이 관리하지 않는 프로세스의 재전송·telemetry를 앱의 HTTP 필터만으로 완전 차단했다고 주장할 수 없다. 엄격한 로컬 전용 보장은 관리 가능한 실행 환경/egress 통제와 검증을 전제로 하며, 그 조건을 충족하지 못하면 “외부 전송 없음 확인 불가”로 표시하고 실행을 보류한다. [Local FAQ의 cloud 설정](https://docs.ollama.com/faq#how-do-i-disable-ollamas-cloud-features)

## 7. 비용 상한의 의미와 한계

비용 제한은 **Recoryn이 발행하는 새 요청의 예산 통제**다. 제공업체의 청구 총액·환율·세금·외부 앱 사용·취소 후 처리 비용을 보장하는 금융 한도가 아니다. UI는 예상/예약/확인된 사용/결과 불명 비용을 분리하고 통화·가격표 시점을 표시한다. 로컬 모델도 전기·시간 비용이 0이라고 표시하지 않는다.

ledger의 `confirmed`, `reserved`, `unknown_exposure`는 서로 겹치지 않는 금액 범주다. 결과 불명 시 해당 예약액을 `reserved`에서 `unknown_exposure`로 옮기며 두 번 합산하지 않는다. 나중에 정산 정보가 도착하면 같은 요청 ID에 연결해 범주를 전환한다. 확정 사용액이 예상보다 크면 추가 dispatch를 막고 초과·가격 추정 오류를 알린다.

| 시점 | 제안 동작 |
| --- | --- |
| 계획 | STT 업로드 길이/바이트, 요약 입력·최대 출력, 중간/통합 호출, 계획된 재시도를 합쳐 산정한다. 외부 STT·요약 모두 공유 예산에 반영한다. 입력 및 출력 한도 강제 지원을 어댑터별 확인한다. |
| 예약 | 통화와 기간 범위가 정해진 영속 ledger에서 `confirmed + reserved + unknown_exposure + next_upper_bound <= limit`를 원자적으로 검사한다. 병렬 작업이 같은 잔액을 각각 쓰지 않게 한다. 가격표 변경으로 기존 계획의 상한이 성립하지 않으면 다시 계획한다. |
| dispatch | 유효한 비용 예약과 권한을 확인한다. 상한을 산정할 수 없거나 강제할 수 없는 제공업체는 “엄격한 앱 예산 모드 지원 불가”로 차단한다. 추정 모드는 별도 선택으로만 허용하고 보장 수준을 표시한다. |
| 응답 | 보고된 usage와 실제 확인 가능한 비용을 대조한다. 잠정 usage를 최종 청구액으로 표시하지 않는다. 확인된 정산 후 차액만 반환한다. |
| timeout/취소/재시작 | 이미 접수됐을 수 있는 요청은 예약을 즉시 반환하지 않고 `unknown_exposure`로 남긴다. 로컬 재시작 후 ledger를 복구하며 동일 요청을 자동 재전송하지 않는다. 제공업체 조회가 지원될 때만 승인된 제어 조회로 상태를 확인한다. |
| 재시도/재개 | 각 새 요청마다 추가 예약한다. 결과 불명 요청의 중복 과금 가능성을 알리고 재시도 선택과 예산을 확인한다. 최대 시도 수와 총 계획 예산을 초과하면 중단한다. 재개로 잔여 예산을 초기화하지 않는다. |
| 한도 도달 | `WAITING_USER`와 남은 범위를 표시한다. “로컬 제공업체 선택”, “범위 줄이기”, “상한 변경 후 재개”, “취소”를 제공한다. 녹음과 이미 저장한 결과는 계속 사용 가능하다. |

사용자가 앱 한도를 바꾸면 변경 이력을 저장하되 API 키나 전사 본문을 기록하지 않는다. 여러 통화는 임의 합산하지 않으며 환산을 지원할 경우 환율·기준 시점·오차 정책을 결정해야 한다. 초기 제안은 통화별 ledger다. 제공업체 자체 계정 한도는 별도 설정이며 하드 한도 여부를 확인하기 전 보장을 문구에 넣지 않는다.

## 8. 녹음·복구·접근성 UX

### 8.1 상태를 분리해 보여주기

화면 상단에 **녹음 상태와 저장 상태**를 고정하고 별도 영역에 STT/요약 작업을 표시한다. `녹음 중`, `일시정지`, `정지 처리 중`, `저장 확인됨`, `저장 장애`, `복구 검토 필요`를 구별한다. “완료” 한 단어로 녹음·파일 확정·전사·요약을 합치지 않는다. 상세 캡처 상태명과 시간축 의미는 D02 계약에 맞춘다.

- 시작 전: 트랙별 장치·미터, 출력 위치/디스크 상태, AI 사용 여부, 필요한 모델·권한 상태를 보여준다. 모델 준비 실패는 녹음 시작을 막지 않는다. 실제 오디오 저장 준비 실패는 녹음 시작 실패로 정확히 표시한다. 녹음 동의 안내는 외부 전송 동의와 별도다.
- 녹음 중: REC 텍스트/아이콘, 경과 녹음 시간, 실제 트랙 상태, 마지막 저장 확인 지점, AI 처리 지연을 표시한다. 일시정지 시간과 결손 구간을 구분한다. 무음 미터는 장치 오류의 확증이 아니며 신호 없음과 장치 분리를 구별한다.
- 정지: 정지 버튼은 한 번의 동작으로 요청하고 반복 클릭에 멱등적으로 반응한다. “원본 저장 마무리 중” 다음 “녹음 저장 확인됨 · 전사 처리 중”으로 전환한다. 모델 종료를 기다리느라 정지 UI가 멈추면 안 된다. “저장 확인”은 확인된 파일/manifest 범위이며 전원 장애 내구성 보장 문구가 아니다.
- AI 결과: `초안`, `후처리`, `사용자 편집` 탭/배지, revision 생성 시각, coverage와 갱신 여부를 표시한다. 근거 선택 시 해당 revision·트랙을 열고 시간으로 이동한다. 텍스트 선택만으로 재생을 시작하지 않고 재생은 별도 명령으로 한다.
- 앱 닫기: 녹음 중에는 “녹음 정지 후 종료 / 계속 녹음”을 선택하게 하고 현재 상태를 알린다. AI만 실행 중이면 “작업 취소 후 종료 / 계속 작업”을 제공한다. 백그라운드 지속이 실제 지원·검증되지 않았다면 종료 뒤 계속된다고 안내하지 않는다.

### 8.2 취소와 복구의 구체 동작

AI 작업 행마다 “취소”를 제공하고 녹음 정지와 시각·접근성 이름을 구별한다. 취소 요청 즉시 `취소 요청됨`을 표시하고 새 하위 작업·재시도를 막는다. worker 응답 또는 로컬 격리 종료 후 `취소됨 · 부분 결과 보존`으로 표시한다. 원격 상태를 확인 못하면 `로컬 대기 종료 · 서버 처리 상태 미확인`을 표시한다. 취소 직후 도착한 결과는 현재 결과로 자동 게시하지 않고 별도 회수 결과로 보존한다. 취소와 완료 경쟁의 확정 규칙은 D01 작업 상태 계약과 통합한다.

재시작 시 복구 화면에는 세션별 마지막 확인된 녹음 시각, 복구 가능한 트랙/청크, 미확정·손상·결손 범위, AI 체크포인트, 결과 불명 원격 요청을 표시한다. 후보를 “정상 복구 완료”로 미리 표시하지 않는다. “복구 결과 검토”, “확인된 구간 재생”, “새 구간 녹음”, “AI 이어서 처리”, “지금은 닫기”를 제공한다. 손상 파일 자동 삭제나 녹음 자동 재시작은 하지 않는다.

“새 구간 녹음”은 중단 이후 새 capture interval을 만든다. 절전·강제 종료 동안의 소리를 복원한다고 표현하지 않는다. 복구 전사는 확인 가능한 미디어 범위에 대해서만 실행하며 gap을 유지한다. 디스크 부족·저장 실패에서는 AI 대기보다 캡처 위험을 상단에 우선 표시하고, 계속 기록할 수 없는 상태를 REC 정상 표시로 남기지 않는다. 장치 대체·다른 저장 위치 사용의 구체 정책과 복구 가능 범위는 D02 결정에 연결한다.

### 8.3 에러 화면과 접근성

에러 상세에는 `무슨 일이 발생했는지 → 영향받은 작업/범위 → 저장된 것 → 지금 가능한 행동 → 진단 ID` 순서로 제공한다. AI 예외는 비차단 작업 패널에, 실제 캡처·저장 장애는 지속되는 상단 경고에 표시한다. 권한·비용·장치 전환 화면은 기본 선택을 허용으로 두지 않는다. “녹음은 계속 중”은 실제 캡처 상태가 확인될 때만 쓴다.

| 상황 | 사용자가 보는 상태 | 복구 동작/금지 |
| --- | --- | --- |
| 모델 없음/의존성 누락 | “녹음 사용 가능 · 로컬 전사 준비 필요” | 명시적 설치 안내, AI 끄기. 자동 다운로드 금지. |
| STT 중단/지연 | 초안의 마지막 처리 시간, 남은 범위, “녹음 상태” 별도 표시 | AI 재시도/취소, 종료 후 처리. 초안을 확정본으로 표시하지 않음. |
| 요약 schema/근거 검증 실패 | “요약 검토 필요”, 정상 구간과 실패 구간 | 유한 재시도/수정 입력/부분 결과 보기. 정상 요약 자동 대체 금지. |
| 인증/동의 실패 | “전송하지 않음” 또는 실제 전송 여부와 차단 이유 | 인증 설정/범위별 동의. 키 저장만으로 재전송하지 않음. |
| 외부 timeout | “수신 확인 안 됨 · 서버 처리/비용 미확인” | 상태 확인 가능 여부 표시, 사용자가 선택한 재시도. 자동 중복 호출 금지. |
| GPU/비용/컨텍스트 초과 | 실패 이유, 미처리 범위, 유지된 결과 | CPU 동의/예산 조정/재분할. 전송·모델 변경 권한 별도. |
| 장치 분리·절전·디스크 문제 | 영향 트랙·마지막 확인 시각·결손 가능 구간 | D02가 확인한 새 구간/복구 선택. “누락 없음” 주장 금지. |
| 손상된 근거/옛 revision | “근거 사용 불가” 또는 “이전 전사 기반” | 원 revision 열기/복원/재요약. 현재 텍스트에 자동 재연결 금지. |

접근성 수락 조건은 다음과 같다. PySide6가 이 조건을 자동 충족한다고 가정하지 않고 실제 Windows 화면 읽기 도구로 검증한다.

- 모든 녹음/정지/일시정지/작업 취소/동의/근거 이동/복구 행동을 키보드로 수행할 수 있어야 한다. 논리적 탭 순서, 보이는 포커스, 접근성 이름·역할·상태를 제공한다. 단축키는 표시·재설정 가능하게 하고 텍스트 편집 중 REC 단축키의 오작동을 막는다.
- REC·오류·권한·근거 검토 상태는 색상 외 텍스트와 형태로 표현한다. 깜박임·자동 스크롤을 끌 수 있고 새 초안 도착으로 입력 포커스/선택 위치를 옮기지 않는다.
- 화면 읽기는 상태 전환·중요 오류만 알리고 경과 시간·미터·매 토큰을 지속 발화하지 않는다. 알림 후 현재 작업으로 포커스를 돌릴 수 있어야 한다. 그래픽 미터에 텍스트 상태를 제공한다.
- 고대비·큰 글꼴·Windows 배율에서 핵심 동작과 경고가 잘리지 않아야 한다. 긴 파일명·긴 한국어 문장·혼합 언어·한글 IME 조합 중 revision 갱신을 검증한다. 지원 배율과 화면 크기의 구체 매트릭스는 D04가 확정한다.
- 모달 동의창에는 목적·수신자·데이터 범위·비용·취소를 읽을 수 있는 순서로 배치한다. `Esc`는 동의를 허용하지 않고 닫기/거부로 작동한다. 복구 화면도 키보드만으로 검토·닫기 가능해야 한다.

## 9. 검증 가능한 수락 기준 제안

다음은 **앞으로 수행할 시험 명세**이며 이 문서 작성 중 통과한 제품 시험이 아니다. mock provider/가상 미디어 시험과 Windows 실기 시험을 분리한다. 실패 주입 결과에는 입력·모델·어댑터·환경·로그 가림·예산 ledger·원본 해시를 확인 가능한 범위로 남긴다. 실제 녹음 품질·캡처 손실 판단은 D02/D04 시험에 의존한다.

| ID / 원칙 | 시험과 통과 조건 |
| --- | --- |
| AU01 / R01,R06 | AI 의존성·모델·Ollama 없는 환경에서 녹음 전용 화면을 열고 저장을 수행한다. AI 영역만 사용 불가이며 모델 다운로드/외부 연결 시도는 0건이어야 한다. |
| AU02 / R01,R03 | 느린 STT·요약 예외·worker 종료를 주입한다. 캡처 저장 경로가 해당 worker를 기다리지 않고, 원본을 수정하지 않으며 AI 실패가 녹음 정지 명령을 만들지 않아야 한다. 실제 무손실 여부는 별도 계측한다. |
| AU03 / R06 | streaming/word timestamp/화자 구분 미지원 descriptor를 사용한다. UI와 계획은 미지원 표시·대체 표현을 일치시키며 미지원 API를 호출하지 않아야 한다. |
| AU04 / R03,R04 | draft 두 개, corrected, edited 두 개를 순서대로 게시한다. 각 ID·해시와 기존 내용은 불변이고 이전 revision 열기·편집 취소·동시 편집 충돌 감지가 가능해야 한다. |

## 11. 확인한 1차 자료와 검증 한계

공식 문서 확인일은 2026-11-14다. 문서의 기능 설명을 확인했으며 라이브러리 설치, API 실행, 모델 다운로드는 하지 않았다. 공급자 문서는 변경되므로 구현 시 고정 버전에서 재확인해야 한다.

- [Faster-Whisper 공식 README](https://github.com/SYSTRAN/faster-whisper): word timestamp와 VAD 사용 예, batch VAD 기본 동작 설명을 확인했다. 이로부터 네이티브 streaming, 정렬 정확성, 특정 GPU 호환성을 보장하지 않는다.
- [Ollama Local FAQ](https://docs.ollama.com/faq): loopback 바인딩, 주소 변경, CPU/GPU 배치 표시, cloud 기능 비활성화 설정을 확인했다. Recoryn에서 강제할 수 있는지와 서버 외부 전송 차단은 검증하지 않았다.
- [Ollama 인증 문서](https://docs.ollama.com/api/authentication): 로컬 API 인증 설명과 로컬 API를 통한 cloud 모델 호출 예를 확인했다. loopback만으로 로컬 실행을 판정하지 않는 설계의 근거다.
- [Ollama context length](https://docs.ollama.com/context-length): 컨텍스트 설정·메모리 영향 설명을 확인했다. FAQ와 이 문서의 기본 컨텍스트 설명이 일치하지 않아 고정 기본값을 계약에 넣지 않았다. 실제 런타임·모델·요청에 적용되는 한도를 확인해야 한다.

문서 작성 중 검증은 입력 요구사항과 제안의 구분, D03 범위의 정적 계약·오류·수락 기준·링크 검사에 한정한다. 로컬 문서 링크의 대상 존재, 코드 fence 짝, UTF-8 대체 문자 및 줄 끝 공백 부재와 AU01~AU21의 21개 수락 기준을 확인했다. 주소의 위치와 실제 실행 위치의 열거형을 일치시키고 예산 범주의 중복 합산을 방지하도록 명세를 점검했다. AU 시험, 음성 품질 측정, 실제 네트워크 차단, Windows 접근성 및 하드웨어 검증은 모두 미수행이다.
